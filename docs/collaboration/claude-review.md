## 1. 五个最高优先级的反对意见

**① 平台范围与关键路径不匹配**
- MVP 同时要求 Web、原生 iOS + HealthKit、中英双语和化验单。
- 但是否有 Mac、Xcode 和 Apple 开发者会员仍未知,这是硬阻塞。
- [建议] 先定一个"全流程主客户端",另一端后跟。共享 API 和数据模型从第一天起统一。
- 若 Apple 条件暂缺:Web 先跑通全流程(睡眠手动录入,拍照用浏览器相机);iOS 作为第二个客户端,补上 HealthKit。

**② "全球用户 + 中文"带来数据驻留和合规冲突,化验单进一步放大风险** [需核实]
- 健康数据在 GDPR 中属于特殊类别,在 PIPL 中属于敏感个人信息,还可能涉及跨境传输。
- 美国方面需关注 FTC 健康数据泄露通知规则、华盛顿州 MHMDA 等。
- 若覆盖中国大陆,可能需要 ICP 备案和生成式 AI 备案,且部分海外 LLM 不可用。
- Apple 对 HealthKit 数据用途、以及"向第三方 AI 共享个人数据"有披露和授权要求。
- 结论:必须先回答"中文是指语言,还是指大陆市场"。

**③ 调整引擎不能让 AI 做决策** [建议]
- "可解释"要求每条建议的触发条件可以复现。
- 做法:确定性规则库生成候选调整和结构化理由(引用具体数据点);LLM 只负责措辞,输出经 schema 校验。
- 否则必然出现隐含的因果推断和编造的理由,违背产品原则。

**④ 源码复用的预期应降到"参考"**
- [已核实] SparkyFitness 许可证存在冲突;Mealie 是 AGPL。
- [建议] 默认采用 clean-room 方式:只借鉴字段和交互思路,不复制代码与 schema。FudAI 和 openGym 未核实前同样处理。
- 理由:数据模型不一致的代价,远高于复用带来的节省。

**⑤ 拍照记录的精度和单位成本未建模**
- 照片估算份量误差大,中餐混合菜尤其明显。
- 每张照片的 AI 成本,乘以活跃频率,再对照约 20 美元定价,尚未测算。
- 差异化在"每日行动",不应在识别精度上和 Cal AI 硬拼。
- [建议] 优先做好"快速修正"体验;显示份量不确定区间;设置单用户每日 AI 调用上限;抽象模型提供方接口,避免锁定。

## 2. 最小但完整的第一版(保留全流程) [建议]

| 环节 | v1 最小形态 |
|---|---|
| 渐进 onboarding | 4–5 屏:目标(表现/体成分/习惯)、训练频率、可选体征、过敏与饮食限制、同意书和排除项筛查(年龄、孕期、肾病、糖尿病用药等)。其余问题在使用中逐步询问。 |
| 计划确认 | 由确定性公式给出范围(维持热量区间、蛋白 g/kg 区间),默认不设赤字;从少量训练模板中选择;用户确认后生成计划 v1。 |
| 饮食记录 | 拍照、文字、手动三种入口共用同一个编辑器。AI 只出草稿,用户逐项改食物、份量和宏量后才能保存。食物库建议用公共领域数据(如 USDA FDC)。中文食物成分数据的授权 [需核实]。 |
| 训练记录 | 组数 × 次数 × 重量,或时长 + RPE;用规则做进阶提示(例如双重进阶)。 |
| 睡眠与状态 | iOS 读取 HealthKit 睡眠数据;Web 手动录入;每日 1–5 分的精力和酸痛自评。 |
| 调整建议 | 每天最多 3 条。约 10 条规则。每条都有理由、引用的数据和前后 diff,可接受或撤销。 |
| 周回顾 | 聚合数据并标注完整度,例如"7 天中记录了 4 天"。 |
| 化验单(晚期、功能开关) | 上传 → OCR 草稿 → 用户校正 → 保存原值、原单位、原参考范围、采样日期和来源文件 → 单指标趋势 → 通用说明加"请咨询医生"。**v1 中化验单不连接调整引擎。** |
| 底座 | 同意书审计、导出和删除、私有存储、按账户隔离。 |

**明确不做**:支付、Android、聊天教练、社交、条码扫描、微量营养素、补剂剂量、其他可穿戴设备。

## 3. 数据和 API 不变量 [建议]

### 计划与建议
1. `plan_versions` 只追加,不可修改。`plans.current_version_id` 是唯一指针。每个版本记录 `parent_version_id`、`created_by(user|accepted_proposal)` 和 `reason`。
2. AI 和规则的输出只能写入 `proposals`,绝不直接改计划。proposal 需记录:
   - `base_version_id`
   - `diff`
   - `rule_ids`
   - `evidence_refs`
   - `model`
   - `prompt_version`
   - `input_hash`
   - `validation_status`
   - `status`(proposed / accepted / rejected / expired / undone)
3. 接受操作是一个事务:若 `current != base`,返回 409 并要求重新生成。离线时可以排队,但必须经服务端确认后才生效。
4. 撤销 = 新建一个内容等于父版本的版本。不删除记录,不改写历史。
5. 每条每日行动都记录它来源的 `plan_version_id`。

### 记录与计算
6. 营养总量一律由服务端根据"条目 × 份量"确定性计算,忽略客户端上报的总数。数值以规范单位存储(g、kcal、mg),同时保留原始输入单位。
7. 原始测量值和 AI 草稿分表存储。用户确认后的条目通过 `draft_id` 关联草稿。
8. 缺失不等于零:
   - 每日记录状态分为 `unlogged`、`partial`、`user_marked_complete`;聚合计算时排除 unlogged。
   - 没有睡眠样本时值为 `null`。
   - 所有派生值都要携带完整度。

### 离线与 HealthKit 同步
9. 所有客户端创建的记录都使用客户端生成的 UUID 作为幂等键,POST 实现为幂等 upsert。可编辑实体带 `revision`;不匹配时返回冲突,由客户端展示并让用户选择。修订历史全部保留。
10. HealthKit 原始样本:
    - 唯一键为 `(user_id, 'healthkit', hk_uuid)`。
    - 保存 source bundle、设备、开始和结束时间、时区偏移、原值和原单位。
    - 使用 anchored query 的删除事件生成 tombstone(软删除)。
    - 每种数据类型的 anchor 存在设备端。HealthKit 是这些数据的权威来源,服务端只做镜像。
11. 多来源重叠时(Watch、iPhone、第三方 App、手动):原始数据全部保留,按带版本号的确定性优先级规则派生"睡眠会话"。用户可以设置来源偏好。
12. 时间存储为 UTC 时刻、IANA 时区和本地日期。睡眠按醒来日期归属到某一天。
13. 每行数据都带 `user_id`,由服务层或 RLS 强制隔离。对象存储按用户划分路径,签名 URL 设短 TTL。
14. 处理任何数据前检查对应的同意范围。用户撤回同意后停止处理;删除操作要级联到对象存储,以及 AI 提供方的留存数据(具体保留条款 [需核实])。

## 4. 安全缺口

### 运动表现营养 [建议,建议请注册营养师审核]
- **低能量可用性 / RED-S**
  - 需要摄入下限和最大减重速率(例如每周不超过体重的 0.5–1%,待专业确认)。
  - 记录摄入明显偏低时,先询问是否漏记,不直接给出结论。
- **进食障碍风险**:提供隐藏数字的模式;避免用"超标"这类语言;设成年年龄门槛(建议 18 岁以上)。
- **排除和保守模式**:孕期及哺乳期、肾病(高蛋白不适用)、糖尿病或胰岛素使用者、正在服药者。
- **过敏**:规则只能基于标签做排除,不能检测照片里隐藏的过敏原。绝不显示"对过敏安全"。
- **范围外内容**:补剂剂量、脱水降体重、极端热环境。
- **其他**:kcal/kJ 和 lb/kg 的换算,以及中餐份量估计的误差,都要向用户可见地呈现。

### 化验单解读
- 只使用报告自带的参考范围,不套用通用范围。
- 单位换算需按指标使用专用系数表(例如 mg/dL 与 mmol/L);系数未知时不做换算。
- OCR 高风险点需要专门校验:
  - 小数点
  - "<0.5" 这类截断值
  - 定性结果
  - H/L 标记
  - 采样日期与报告日期的区别
- 跨实验室、方法或单位变化时,趋势图要明确标注"不可直接比较"。
- 报告上带危急值标记时:只提示"请尽快联系医疗人员",不做任何解读。
- 文档中的文字一律视为数据,防止通过图片或 PDF 文本进行提示注入。
- 只允许上传本人报告。
- 解读功能可能触及医疗器械软件的边界(FDA、EU MDR、NMPA)[需核实]。这是化验单放在晚期并单独做法律评审的主要理由。
