## 4. 调用链与窗口包含关系

### 首页

1. `Dashboard:32` → `localDate()` → `types:276–282`：默认参数取得当前时刻；`Intl.DateTimeFormat`未传timeZone，所以取浏览器/宿主默认时区。helper已用Gregorian、拉丁数字和formatToParts组装日期键。
2. `Dashboard:34–42`：按该today等值匹配三类记录及`completedActions[today]`。
3. `Dashboard:43–52`：循环内每次重新取当前时刻，按浏览器本地`setDate(getDate()-6+i)`生成日期，再用同一浏览器时区取键和星期标签。
4. `Dashboard:53–60、349–375`：按这些键筛选七日记录、图柱及今日标记。单次稳定时钟下，实际是**今天及之前六个日历日**，不是周一至周日，也不是过去168小时。
5. `Dashboard:100–110`：行动点击使用闭包中的today保存一个`completedActions`键；此链不只有显示影响。该保存保留其他旧键，但当前新写入归日仍由浏览器today决定。

### 趋势

1. `Trends:178–185`：档案timezone非null/undefined时优先使用，否则用浏览器resolvedOptions时区；把格式化结果作为today。
2. `Trends:164–169、199`：把today当作`YYYY-MM-DD`解析到人造UTC中午，使用`setUTCDate`生成`today-(range-1)`至today，首尾都包含；默认7，也可切14。
3. `Trends:190–214`：原记录date直接分组，窗口用日期键查Map，没有把记录时刻转换为档案时区后重新归日。
4. `Trends:218–230、394–457、525`：默认选窗口最后一天；选中/标签仍依据date键。标签显式UTC，因此浏览器/档案时区不会把这个人造锚点显示成相邻一天。

**当前可核的包含关系**：两页算法都实现滚动窗口且包含今天，前提是today合法且时钟稳定；窗口端点的时区选择却不一致。首页“本周节奏/本周已完成”（343/383）与趋势“最近7天/Last 7 days”措辞不同，现有依据未决定自然周起点。建议此次最小候选保留最近7个日历日并统一说明；这是建议，不把自然周或排除今天写成已约定产品规则。

## 5. 静态发现与限制

### F1：今日、七日边界及行动新写入的时区口径不同——确认

`Dashboard:32、43–50`使用浏览器默认时区，`Trends:178–185`优先档案时区。仅凭这条代码链即可确认选择策略不同，无须假设数据库出错。

合成例子的手工推导：固定`2026-10-17T06:30:00Z`，浏览器America/Los_Angeles当时为10月16日23:30，档案Asia/Shanghai为10月17日14:30。首页today为`2026-10-16`、七日为10–16日；趋势today意图为`2026-10-17`、七日为11–17日（后者还以格式字符串满足日期解析前提）。因此同一保存的17日记录可在趋势最后一日出现，但不会进入首页今日筛选；首页行动点击也使用16日键。

结论是**静态口径不一致**；不是本轮挂载页面/保存复现，也不证明历史健康事实已经被改写或丢失。哪一时区应作为统一权威仍须确认候选契约。

### F2：无效的非空档案时区没有显示层回退——有条件确认

`Trends:180–181`只有nullish回退，没有校验或异常恢复。若传入`""`、未知时区等无效非nullish字符串，构造formatter时会失败，回退表达式不会改用浏览器时区。`Profile.timezone`虽然类型要求string（types:23），类型不等于运行时IANA有效性校验。

本轮未读上游验证，不能断言普通设置操作能产生这种状态。这里只确认注入旧/异常状态时该消费链缺少回退；实际用户可达性、错误边界和页面表现均NOT RUN。profile缺失或timezone为null/undefined时，现有代码**已有**浏览器回退，不能描述成全部缺失场景都会失败。

### R1：本地化显示字符串被当机器日期键——契约风险，未证明当前运行时故障

`Trends:178–185`直接使用`Intl.DateTimeFormat("en-CA").format(...)`，随后164–169按ISO式日期键拼接解析。代码依赖该locale的最终显示格式恰好是所需键；没有像`types:277–282`那样明确抽取年/月/日、Gregorian和拉丁数字后组装。

应把机器日期序列化与用户显示格式分开；不能仅用locale名称充当序列化协议。若输出不是可用的`YYYY-MM-DD`，后续解析/`toISOString()`存在失败路径。本轮没有执行Intl、采样任何浏览器/ICU版本或复现不同格式；不声称当前网站已经因此崩溃。

### R2：首页多次读取时钟，跨午夜的同一渲染可能自相矛盾——边界风险

`Dashboard:32`取得today后，43–45又为七个条目分别取时刻。如果一次渲染恰跨本地午夜，today与窗口尾日可能来自不同日，甚至循环前后产生不连续的日期集合。这是代码允许的边界条件，不是已经发生的实测事故。趋势的窗口从同一today派生，没有同样的逐项墙钟读取。

三文件内没有独立的午夜刷新调度；本轮不读App/其他重渲染来源，不能据此断言整站不会自动更新。最小候选先保证一次计算同一时刻；页面长驻至午夜后何时触发重算是另待明确的生命周期要求，不顺便新增计时器。

### 已存在且应保留的正确行为

- 两页在各自日期口径、合法输入和稳定时钟前提下，都包含末日与此前六日；没有依据指控普通七天窗口少一天。
- 首页本地`setDate`与趋势UTC日历步进均在做日历运算，不能笼统改为每次减`86_400_000`毫秒，或把DST本身当作现有必现错误。
- Trends的UTC锚点、UTC步进和UTC标签互相配套；`toISOString().slice(0,10)`在这条**人造UTC锚点**链中有明确用途，不是所有ISO截日期都应删除。
- 原记录按保存date分组；睡眠时刻用于经过时长，不在本链里重算睡眠归属日。睡眠合并/舍入等算法不属于此次重构范围。
- 无记录日期的指标保留null/`—`；不能为统一日期而补零、补假记录或改变完整度定义。
