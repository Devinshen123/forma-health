## Confirmed finding: cleanup rollback restores metadata after bytes have been removed

**Medium severity, reproduced in an isolated synthetic database.** `Store.completeAssetCleanup` invokes `deleteUnreferencedAsset` within its SQLite transaction. That function deletes the asset row and runs `rmSync` before the outer transaction commits. Abrupt process loss in that window lets SQLite restore the row, draft references and intent, while the filesystem cannot restore the deleted bytes. Current state validation checks asset metadata, so a subsequently submitted report may reference this unusable attachment successfully.

The test-only child overrides its own `db.exec` to exit **only itself** with code 73 when the transaction reaches `COMMIT`. There is no production failpoint, signal sent to other processes, server change or database migration. For cleanup, the synchronous file removal has finished before this exact exit boundary. A fresh app/Store then opens the same disposable SQLite file and serves random loopback HTTP:

| Observation | Actual |
|---|---|
| Child attests cleanup pre-COMMIT failpoint | exit 73, no signal |
| Asset metadata / original cleanup intent after reopening | present / present |
| Original private PDF bytes after reopening | absent |
| Owner GET `/api/assets/:id` before new reference | 500 |
| New report upsert referencing that attachment | POST `/api/sync` 200 |
| Original removal receipt replay after re-reference | 200; intent consumed |
| Current report / later owner asset GET | references missing bytes / 500 |
| Never-saved candidate and other owner's PDF | 200; bytes exactly match originals |
| Another owner GET for damaged attachment | 404 |

The invariant assertion is deliberately **failing**: if attachment metadata survives restart, its original bytes must remain readable. No skip, TODO or inverted expectation hides the defect. Independent tests that merely ABORT the SQL row deletion before `rmSync` do not cover this window.

Small bounded follow-up: asset-reference validation can reject an attachment whose bytes are unavailable, preventing a newly accepted broken report. That does not repair lost bytes, earlier broken records, legacy receipts or cross-resource crash atomicity. A full deletion/recovery protocol needs an explicit durable staging/tombstone design and retention decision; this review does not implement one or scan for unreferenced uploads. Coordinator was notified immediately after reproduction and retains responsibility for authorizing any product patch.

## Passing controls and legacy limits

1. **Legacy hash-only receipt:** construct the exact persisted shape using synthetic Store data (committed next state plus `sync_mutations.payload_hash`, no cleanup intent). Same-receipt HTTP replay returns 200 and the unchanged snapshot. A changed payload reusing that receipt returns 409. No intent is invented; the formerly referenced asset, never-saved candidate and other owner's asset retain exact bytes. Cross-owner access remains 404. This proves conservative behavior when history is missing; it does **not** reconstruct which historical assets should have been deleted. The fixture uses baseline `Store.save`, which does not record PUT intents; do not blindly reuse that setup against a future implementation that does.
2. **State/sync pre-COMMIT control:** the child exits at the same transaction boundary while committing the record removal and its receipt/intent. Reopening proves state, revision, entity versions, receipt and intent rolled back together; original PDF bytes survive. This isolates the failed guarantee to the irreversible filesystem operation rather than claiming SQLite transactions are broken.
