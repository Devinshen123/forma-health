# B-18 PUT cleanup recovery: implementation and evidence

Codex `/root/forma_backend_20261018` implemented this bounded change on `codex/forma-put-cleanup-retry-20261018`, from task-entry commit `1c085362becdd6365be9799bb01d68e03263b39f` (product baseline `85912f2d85f5758e88686950c870990a8acf008a`). This is an implementation report, not an independent Claude approval.

## Confirmed problem

A synthetic `BEFORE DELETE ON assets` SQLite abort makes PUT `/api/state` return 500 after its state/revision transaction has already committed. The original request's revision is now stale. After removing the fault and restarting the app/Store, retrying that PUT returns the existing 409 response but previously left the removed attachment readable (HTTP 200 instead of 404). The pre-fix test reached precisely that assertion; it did not fail on setup, imports or the first write.

## Bounded behavior

The existing `asset_cleanup_intents` table now receives precise owner/asset removal intents within `Store.save`, in the same transaction as state/revision/entity versions. The internal identifier is `put-state:<inputRevision>`; externally accepted sync IDs are UUIDs. The existing owner/current-reference-checked cleanup consumes each exact intent after a save, or during a fully parsed authenticated stale PUT before its unchanged 409 response. An ongoing cleanup failure retains the intent while keeping that conflict response. The state payload of a stale retry is never applied and never determines cleanup candidates.

No DDL, HTTP route, response schema, 200/400/401/409 contract, UUID sync receipt behavior, cleanup retention policy or client changes were introduced. Newly committed PUTs retain the existing 500 behavior if their post-commit cleanup fails. No scans of uploads, unsaved drafts or old hash receipts occur.

## Missing-byte reference guard after `d824f31`

`Store.assetBytesAvailable` checks owner-specific file metadata without reading the complete image/PDF. Missing paths and non-files fail the existing attachment-unavailable validation. Metadata lookup remains unchanged: exact old intents must still be able to retire a retained asset row. Validation runs inside the sync transaction and, using a new optional `Store.save` validator, inside PUT's state-write transaction after its CAS check. No new HTTP schema, DDL, cleanup policy or product test hook is involved.

Three real pre-fix failures are in `backend/red-missing-bytes-guard.log` and its metadata: sync, PUT and a second-Store deletion before save each returned 200 instead of 400. The same three scenarios are green after the guard. Focused PUT+sync recovery is **20/20**; the complete suite is **223/223**, exit 0, no failed/skipped/cancelled/todo tests. Separate `focused-put-sync-guard` and `full-suite-guard` log/metadata files preserve the earlier 220-test evidence.

The missing-byte fixtures deliberately reconstruct the observed on-disk condition; they do not claim to repair the original crash. Public HTTP assertions show no state/revision/entity-version change, reuse of the rejected save identity with an available candidate, preserved candidate/other-owner bytes, and successful retirement of exact retained cleanup metadata. The PUT race uses a second real Store only in the test fixture, immediately before original `save` entry, and proves validation happens after that deletion under the save lock.

The `DELETE asset row -> rmSync -> COMMIT` crash window remains. This change cannot restore original bytes, repair existing broken references or guarantee SQLite/filesystem atomicity. Historical hash-only receipts cannot reconstruct removed assets; never-retried intents can remain retained. No broad GC, retention strategy or byte journal was added. Final cross-review and independent three-case verification are coordinator-owned and are not claimed here as complete.

This report claims neither complete backup nor full App/build/browser coverage. JSON exports exclude attachment bodies, and server exports also exclude the client's unsynced queue.

Actual Claude reviewer `7bd94c31-1d67-4b13-85e4-b196ac699a2d` identified a Medium regression in the first guard at reviewed HEAD `6739b927eb5c760d8232df970998a11401240d26`: checking bytes for every next-state attachment rejected unrelated PUT and sync writes if an existing record already had missing bytes. The original Claude result/receipt is unchanged. Following coordinator authorization and serial ownership handoff, Codex reproduced both real HTTP failures (400 instead of 200) and narrowed only this byte check.

The final guard compares associations using collection plus record ID plus attachment ID. The original whole-state metadata ownership and MIME checks remain. An unchanged existing association can survive unrelated or other-field edits; missing bytes are checked whenever a record newly references an asset or changes its association. A new record cannot copy the same broken attachment even if the old record still references it, and a different existing record cannot reassign itself to that missing attachment. Removal of the old record succeeds and retires its exact cleanup metadata. No global asset-set shortcut, DDL, retention policy or physical deletion change was added.
