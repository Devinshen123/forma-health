# B-18 PUT cleanup recovery: implementation and evidence

Codex `/root/forma_backend_20261018` implemented this bounded change on `codex/forma-put-cleanup-retry-20261018`, from task-entry commit `1c085362becdd6365be9799bb01d68e03263b39f` (product baseline `85912f2d85f5758e88686950c870990a8acf008a`). This is an implementation report, not an independent Claude approval.

## Confirmed problem

A synthetic `BEFORE DELETE ON assets` SQLite abort makes PUT `/api/state` return 500 after its state/revision transaction has already committed. The original request's revision is now stale. After removing the fault and restarting the app/Store, retrying that PUT returns the existing 409 response but previously left the removed attachment readable (HTTP 200 instead of 404). The pre-fix test reached precisely that assertion; it did not fail on setup, imports or the first write.

## Bounded behavior

The existing `asset_cleanup_intents` table now receives precise owner/asset removal intents within `Store.save`, in the same transaction as state/revision/entity versions. The internal identifier is `put-state:<inputRevision>`; externally accepted sync IDs are UUIDs. The existing owner/current-reference-checked cleanup consumes each exact intent after a save, or during a fully parsed authenticated stale PUT before its unchanged 409 response. An ongoing cleanup failure retains the intent while keeping that conflict response. The state payload of a stale retry is never applied and never determines cleanup candidates.

No DDL, HTTP route, response schema, 200/400/401/409 contract, UUID sync receipt behavior, cleanup retention policy or client changes were introduced. Newly committed PUTs retain the existing 500 behavior if their post-commit cleanup fails. No scans of uploads, unsaved drafts or old hash receipts occur.

## Limits handed to independent review

Existing SQLite/file deletion crash atomicity is not proven. The current cleanup deletes its SQL row and file before transaction COMMIT; a later commit failure or crash is a separate risk for review. Historical receipts without exact intents cannot reconstruct removed assets. Never-retried intents may remain retained. This report claims neither complete backup nor full App/build/browser coverage. JSON exports exclude attachment bodies, and server exports also exclude the client's unsynced queue.
